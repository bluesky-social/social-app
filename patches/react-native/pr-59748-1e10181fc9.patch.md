## ReactAccessibilityDelegate.kt Patch - Content Capture rebuilds accessibility subtrees on the UI thread

On Pixels running Android 16 and 17, Content Capture builds an
`AccessibilityNodeInfo` for every view that appears, on the UI thread, whether
or not an accessibility service is on. Every app gets a session through
Android's scam detection. For React Native views this goes through
`ReactAccessibilityDelegate.getTalkbackDescription`, which initializes each
child's node to check whether it speaks, then calls itself with `null` for that
child. The recursive call builds and initializes the same node again, all the
way down the subtree, so the work grows exponentially with nesting depth.

Upstream issue, with a public repro and profiles:
https://github.com/react/react-native/issues/59743 (100–280ms freezes when a
screen re-appears). We found the same cost while profiling the Home feed's list
on a Pixel 7a (APP-3833): Content Capture was about 20–25% of the main thread
while scrolling, and RN's text accessibility delegate alone about 14%.

Backport of https://github.com/react/react-native/pull/59748: pass the node the
loop already initialized instead of `null`. In 0.88.1,
`createNodeInfoFromView` is exactly `AccessibilityNodeInfoCompat.obtain()` plus
`ViewCompat.onInitializeAccessibilityNodeInfo`, which is what the loop just did
for `childNodeInfo`. `getTalkbackDescription` copies the node it is given with
`obtain(info)` and never recycles it, so descriptions are unchanged. The PR's
test fixture of 8 nested groups goes from 511 node initializations to 9.

The PR is open and unreviewed; the hash in the file name is its head commit,
`1e10181fc9041e7e0dfc5810d31ed31731675646`.

Like every React Native Android patch, this only applies to builds that compile
React Native from source (production builds).
